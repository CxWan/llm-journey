## 一、核心模型：一次调用 = 寄一封信

```
你的程序 ──HTTP POST──▶ 厂商服务器 ──▶ GPU 上的模型 ──▶ 生成文字
         ◀──JSON 响应──
```

一个请求由四部分组成：

| 部分 | 内容 | 类比 |
|---|---|---|
| 方法 + 路径 | `POST https://open.bigmodel.cn/api/paas/v4/chat/completions` | 寄到哪、办什么事 |
| 请求头 | `Authorization: Bearer <key>`<br>`Content-Type: application/json` | 身份证 + 声明内容是 JSON |
| 请求体 | `{"model": "...", "messages": [...]}` | 信的内容 |
| 响应体 | `{"choices":[{"message":{"content":"..."}}], "usage":{...}}` | 回信 |

**结论：所谓"调用大模型"，99% 的场景就是发一个 HTTP POST。**

---

## 二、SDK 与裸 HTTP 的关系

`openai` 这个库**本身没有任何 AI 能力**，它只做三件事：按格式拼请求、发出去、把回信解析成 Python 对象。

```python
# A. SDK（日常用）
client = OpenAI(api_key=..., base_url=...)
resp = client.chat.completions.create(model=..., messages=[...])

# B. 裸 HTTP（理解原理用，urllib 即可复现）
urllib.request.urlopen(Request(url, data=json.dumps({...}), headers={...}))
```

**先看懂 B，再放心用 A。**

## 三、OpenAI 兼容接口：一套 SDK 通吃国内厂商

OpenAI 的接口格式事实上成为行业标准，国内厂商都做了兼容实现，**只有 `base_url` 和 `model` 名不同**。

| 厂商 | base_url | 典型 model |
|---|---|---|
| 智谱 | `https://open.bigmodel.cn/api/paas/v4/` | `glm-4-flash`（免费） |
| DeepSeek | `https://api.deepseek.com/v1/` | `deepseek-chat` |
| ModelScope | `https://api-inference.modelscope.cn/v1/` | `Qwen/Qwen2.5-7B-Instruct` |

注意事项：
- `base_url` **末尾斜杠不能漏**，SDK 会在后面拼 `/chat/completions`
- 换厂商 = 改 3 行：`api_key`、`base_url`、`model`

## 四、messages：大模型"有记忆"是假象（重要）

**大模型本身没有记忆。每次请求都是独立的。**

"多轮对话"= 每一轮把**完整历史**重新发一遍：

```python
# 第 1 轮
[{"role": "user", "content": "我叫小明"}]

# 第 2 轮（把上一轮的问答都带上）
[
  {"role": "user",      "content": "我叫小明"},
  {"role": "assistant", "content": "你好小明"},
  {"role": "user",      "content": "我叫什么？"},
]
```

三个角色：

| role | 谁说的 | 作用 |
|---|---|---|
| `system` | 开发者 | 定规矩（人设、输出格式） |
| `user` | 用户 | 提问 |
| `assistant` | 模型 | 历史回答，回填进上下文 |

**代价**：token 随轮数线性增长 → 真实产品要做历史压缩 / 只留最近 N 轮 / 摘要前文。

> 面试题：「多轮对话怎么实现？」← 标准答案就是上面这套。

## 五、token：计价单位

模型不按字算，按 token 算（分词器切出的片段）。经验值仅供参考：

- 英文 ≈ 1 token / 0.75 词
- 中文 ≈ 1000 汉字 → 700~1500 token（随分词器变化）

**唯一可靠来源是响应里的 `usage`：**

```
CompletionUsage(completion_tokens=36, prompt_tokens=48, total_tokens=84)
```

| 字段 | 含义 | 备注 |
|---|---|---|
| `prompt_tokens` | 发过去的（system + 历史 + 问题） | 历史越长越大 |
| `completion_tokens` | 模型生成的 | 单价通常贵 2~4 倍 |
| `total_tokens` | 两者之和 | 账单 |

---

## 六、三个采样参数

| 参数 | 范围 | 直觉 |
|---|---|---|
| `temperature` | 0–2 | 0 = 最稳最确定；1 = 发散有创意 |
| `top_p` | 0–1 | 与 temperature **二选一**调，别同时动 |
| `max_tokens` | 正整数 | 限制生成长度，防烧钱 |

**生成机制**：预测下一个 token 的概率分布 → 采样 → 拼上去 → 重复。
所以 `temperature=0` 也不是绝对确定，只是尽量取概率最高者。

---

## 七、流式输出

| 方式 | 行为 | 体验 |
|---|---|---|
| 非流式 | 全部生成完一次性返回 | 可能干等 10 秒 |
| 流式（SSE） | 每几个 token 推一段 | 边生成边显示 |

**成本完全一样，只差体验。** D3 手写，D6 做成 `/chat/stream`。

## 八、环境与密钥管理

### 虚拟环境

```
系统 Python 3.14.6
  └─ .venv/   ← 本项目的独立环境，只装本项目的包
```

- 为什么隔离：不同项目可能要求同一个库的不同版本
- `uv` 一个工具管三件事：建虚拟环境、装包（比 pip 快一个数量级）、锁版本（`uv.lock`）

### uv run vs python（必记）

| 命令 | 用的环境 | 结果 |
|---|---|---|
| `python hello_api.py` | 系统 Python | ❌ ModuleNotFoundError |
| `uv run hello_api.py` | 项目 `.venv` | ✅ 正常 |

**本项目一律用 `uv run`。**

### 密钥

- Key 放 `.env`，代码里通过 `os.environ` 读，**永远不写明文在代码里**
- `.env` 必须在 `.gitignore` 里；验证：`git check-ignore -v .env`
- **一旦推上公开仓库，删文件没用**，只能作废重发（历史里仍在）
- 生产环境正规做法：云 KMS / Secrets Manager + 容器环境变量注入

## 九、代码骨架（hello_api.py）

```python
import os
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()                                    # ① 读 .env 进 os.environ

client = OpenAI(                                 # ② 建客户端
    api_key=os.environ["ZHIPU_API_KEY"],
    base_url="https://open.bigmodel.cn/api/paas/v4/",
)

resp = client.chat.completions.create(           # ③ 发请求
    model="glm-4-flash",
    messages=[
        {"role": "system", "content": "你是一个简洁的助手，回答不超过两句话。"},
        {"role": "user", "content": "用一句话解释什么是 RAG。"},
    ],
    temperature=0.7,
)

print(resp.choices[0].message.content)           # ④ 取正文
print(resp.usage)                                #    取账单
```

关键点：

- `resp.choices[0]` —— `choices` 是**列表**（可以 `n=3` 要多个答案）
- `.message.content` —— 有时是 `None`（模型返回工具调用时，D5 会遇到）

## 十二、拓展认知

**① 大模型的本质是预测下一个 token。** 由此可解释三件事：

- 幻觉：优化目标是"像人话"而非"真实"，不知道时也会平滑地编
- RAG 有效：把真实资料塞进 prompt，把"猜"变成"抄"
- CoT 有效：先输出中间步骤 = 给模型更多 token 预算做计算

**② 上下文窗口**：不只限制长度，还限制注意力。塞满长上下文会出现 "lost in the middle"——中间段落被忽略。所以 RAG 的目标不是"全塞进去"，而是"只塞最相关的几段"。

**③ 免费模型先用**：开发阶段用免费/便宜模型把逻辑跑对，上线前再换强模型做对比。免费款常有 QPS 限制，循环请求要 `time.sleep(1)` 防 429。

## 十四、实战踩坑记录（2026-10-29 真实发生）

### 坑 1：`KeyError: 'ZHIPU_API_KEY'`

**现象**

```
File "hello_api.py", line 11, in <module>
    api_key=os.environ["ZHIPU_API_KEY"],
KeyError: 'ZHIPU_API_KEY'
```

**三个可能原因，按概率排序：**

| # | 原因 | 怎么查 |
|---|---|---|
| 1 | `.env` 里只写了 Key，没写 `ZHIPU_API_KEY=` | 看第 1 行有没有等号 |
| 2 | 变量名写在方括号里写错了 | 对比 `.env` 的变量名 |
| 3 | `.env` 被存成带 BOM / 文件名成了 `.env.txt` | 看字节前 3 位是不是 `EF BB BF` |

**本次真实原因（两个原因叠加）：**

① `.env` 内容只有那串 Key，缺少变量名：

```
1b44...FlM2...        ← 错：没有 KEY=VALUE 结构，dotenv 直接跳过整行
```

应为：

```
ZHIPU_API_KEY=1b44...FlM2...
```

② `hello_api.py` 里把 Key 填进了 `os.environ[...]` 的方括号：

```python
# 错：方括号里要填"变量名"，不是"钥匙本身"
api_key=os.environ["1b4471ce10fd4720ab0eacd1f216cfb5.FlM20EWKxip61wq1"],

# 对：
api_key=os.environ["ZHIPU_API_KEY"],
```

**理解要点：`os.environ` 是"环境变量字典"，`[]` 里放的是键名（变量名字符串），不是值。**
Key 的值始终只存在于 `.env` 文件中，代码只引用变量名。

**顺带的安全教训：** 把 Key 写进 `.py` 文件比写进 README 更危险，因为 `.py` 是**会**被提交并公开的（`.env` 才被忽略）。本次发现得早，`git log -S` 确认 Key 从未进入提交。

### 坑 2：`uv add` 报 `tunnel error`

原因：环境变量 `HTTPS_PROXY=http://127.0.0.1:7890` 指向一个没启动的代理。

```powershell
Remove-Item Env:HTTPS_PROXY, Env:HTTP_PROXY -ErrorAction SilentlyContinue
```

### 坑 3：`uv` 不读 pip 的镜像配置

`pip config set` 只影响 pip。uv 要单独配：

```powershell
uv config --global index-url https://pypi.tuna.tsinghua.edu.cn/simple
```

## 十五、第一次调用成功后的真实观察

实际输出（2026-10-29）：

```
RAG是指检索-重写-评估（Retrieval-Augmented Generation），是一种用于生成式模型的文本生成方法。
CompletionUsage(completion_tokens=28, prompt_tokens=25, total_tokens=53)
```

**这个回答是错的**：RAG 的正确全称是 **Retrieval-Augmented Generation（检索增强生成）**，不是"检索-重写-评估"。

模型把英文字母缩写"编"了一个看起来合理的解释——**这就是幻觉（hallucination）最典型的样子：语气自信、格式完整、内容错误。**

记住这个瞬间，它解释了为什么整个第 2 周要学 RAG：
**模型的参数里存的是"概率上像样的文字"，不是"事实"。要事实，得在 prompt 里喂给它。**
